## Commands

```bash
npm run dev        # Next.js dev server (Turbopack)
npm run build       # Production build — the only check that catches async/Server Action errors (see below)
npm run typecheck   # tsc --noEmit, hermetic — no network. Catches most type errors `build` would, but NOT the sync-export-in-'use server'-file class (see below); use as a fast pre-build check, not a `build` replacement
npm run test:run    # Vitest, single run (hermetic — no network)
npm run lint        # ESLint
npm run test:db     # Live DB security posture — real credentials, hits production
npm run types:check # Fails if database.types.ts has drifted from the live schema
```

## Architecture

- Route groups: `src/app/(auth)/` (login/register, public) and `src/app/(app)/` (dashboard/pelanggan/pengaturan/pesanan, behind auth + role checks). Layout for `(app)` composes `AppShell` (client) wrapping `Sidebar`/`TopBar`/children.
- Supabase is **remote-only** — there is no local CLI/`supabase start` workflow. Schema changes go straight to the live project (ref `pjkddahrjjqblexxhaef`, region ap-southeast-1) via the Supabase MCP tools (`apply_migration`, `execute_sql`, `get_advisors`); migration files in `supabase/migrations/` are a record of what's already been applied, not a local source of truth to replay.
- `src/lib/supabase/server.ts` / `client.ts` / `admin.ts` are the only places Supabase clients should be constructed (server component / browser / service-role respectively); `require-owner.ts` wraps the owner-role check used by gated Server Actions.
- `settings` table is a simple key-value store (columns: `key`, `value` text). Two seed rows: `pesanan_locked` and `epson_printer_name`. Readable by any authenticated user (`settings_read`); updatable by owner only (`settings_update`). There is deliberately **no INSERT/DELETE policy** — rows are seeded by migration and the app only ever `UPDATE`s an existing key, which is why both actions that write settings must fail closed when zero rows match. Read it via the server client, not admin.
- **Realtime publication contains `pesanan`, `pelanggan` and `users`** (verified against live 2026-07-31; `replica identity full` on all three). **`item_pesanan` and `pembayaran` must NEVER be added** — their rows contain price/payment data that would leak to helpers via the websocket before the role-aware refetch. That invariant is the one that matters; the member list itself is not sensitive (`pesanan` has no price columns, `pelanggan` is readable by all authenticated users anyway, and RLS limits the `users` WAL image to the helper's own row). `RealtimeRefresh` uses the Realtime event only as a "something changed" signal and refetches via a server query.
- **Pesanan status model**: three values only — `diproses`, `selesai`, `dibatalkan`. New pesanan always inserts as `diproses`. Only the owner can transition status. Helpers have no status-change actions.

## Environment

`.env.example` lists the 3 required vars: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (service-role key is server-only, used by `admin.ts` for user-management actions like `createUser`/`deleteHelper`).

## Codebase conventions

- **`'use server'` files: every export must be `async`.** A sync helper in a Server Actions file compiles fine under `tsc`/`eslint`/`vitest` — including `npm run typecheck` — but breaks `npm run build` ("Server Actions must be async functions"). Always run `npm run build` before calling Server Action changes done — it's the only check that catches this.
- **shadcn here uses Base UI (`@base-ui/react`), not Radix** (`components.json` → `"style": "base-nova"`). Composed components take a `render={<Button .../>}` prop instead of `asChild`. Don't hand-write Radix-pattern code from memory — inspect the generated component after `npx shadcn@latest add <name>`.
- **Owner-gated Server Actions**: use `requireOwner(supabase)` from `src/lib/supabase/require-owner.ts` rather than hand-rolling the auth+role check inline. RLS is the real authorization boundary; this is defense-in-depth.
- **`<form action={fn}>` requires `fn` to return `void | Promise<void>`.** Actions here return `{ error?: string }` for error surfacing, so form-triggered deletes/mutations need a small client component with an `onClick` handler instead (see `DeletePaymentButton.tsx`).
- **Popup-blocker-safe pattern for print/PDF flows**: call `window.open('', '_blank')` synchronously as the *first* statement in the click handler, before any `await` — navigate the captured window reference once async work finishes. Calling `window.open` after an `await` gets blocked by browsers.
- **`pdf` from `@react-pdf/renderer` must be imported inside the click handler, not at module top level.** It pulls in pdfkit and the yoga-layout WASM shim — ~1.4 MB that lands in the route's eager bundle. Lazily importing `DocumentPDF` while `pdf` stayed a static import bought nothing, since both resolve to the same package: `/pesanan/[id]` shipped 1901 KB of eager JS against ~400 KB for every other route until `pdf` moved into the same `await import()`. Measure per-route eager JS from `.next/server/app/**/page_client-reference-manifest.js` (sum the `clientModules[*].chunks`) — `next build` no longer prints bundle sizes.
- **Never pass a `next/dynamic`-wrapped component into `@react-pdf/renderer`'s `pdf()`.** `next/dynamic` wraps a component in `React.lazy` + Suspense, which only `react-dom` knows how to resolve. `pdf()` uses its own non-DOM reconciler and doesn't support Suspense, so it silently renders broken/empty output. If you need code-splitting for a PDF component, resolve it with a plain `await import('...')` inside the click handler instead, then pass the real component to `pdf()`.
- **RLS helper functions that query a table protected by a policy calling that same function need `SECURITY DEFINER`.** Without it the function's internal `SELECT` re-triggers the calling policy → infinite recursion. It may look fine for authenticated users (their row short-circuits the `OR`) but blows up for anonymous requests. Verify with `curl /rest/v1/<table>` using the anon key — `npm run build`/tests won't catch this.
- **Sequence-generating `SECURITY DEFINER` functions (e.g. `kode_pesanan` numbering) should use `INSERT ... ON CONFLICT DO UPDATE ... RETURNING ... INTO`, not a separate `SELECT`/`UPDATE ... WHERE` pair.** A two-statement read-then-write can return zero rows (no existing row for this period yet) and silently produce `NULL`, which then violates a downstream `NOT NULL` constraint. An upsert always affects exactly one row, structurally eliminating that failure class.
- **Postgres check constraints are enforced per-statement, not deferred, even within one migration transaction.** If a migration both backfills a column to satisfy a new shape and drops/relaxes an old constraint that the backfill would transiently violate, the constraint drop must run *before* the backfill `UPDATE`, regardless of the fact that the constrained column or table is dropped later in the same migration.
- **When a migration's backfill `UPDATE` touches a table guarded by a write trigger that assumes a real session (`auth.uid()`), wrap the backfill in `alter table ... disable trigger <name>` / `... enable trigger <name>`.** Migrations run without a real authenticated user, so role-checking triggers will reject the backfill otherwise.
- **Shared client-side UI state needed by sibling Server Components in a layout (e.g. a mobile sidebar-drawer toggle shared between the sidebar and the top bar) can't live in the Server Component layout itself.** Lift it into a small client wrapper component (e.g. `AppShell.tsx`) that holds the `useState` and composes the Server-rendered children as props/`children`, rather than trying to thread state through the Server Component tree.
- **Every UI change must be checked on mobile too, not just desktop.** This app has no desktop-only audience — tables need a `sm:hidden` card layout alongside the `hidden sm:block` table (see `OrderList.tsx`), and any inline editor (e.g. `ItemsSection.tsx`) needs to be checked for how it behaves squeezed into a narrow column/card, not just a wide desktop layout. Don't consider a UI task done until you've reasoned through (or viewed) it at a mobile viewport width.
- **`pg_trigger_depth()` bypass is required when a cascade trigger calls a write-guard trigger on a parent table.** For example, `bump_pesanan_updated_at_from_item` (SECURITY DEFINER, fires on `item_pesanan` writes) does `UPDATE pesanan SET updated_at = now()`, which re-fires `guard_pesanan_write`. That guard runs with the original request's `auth.uid()`, so a helper updating their own item would get rejected because they don't own the pesanan. Fix: add `IF pg_trigger_depth() > 1 THEN RETURN NEW; END IF;` at the top of any write guard that may be invoked by a cascade. This is a latent bug to watch for whenever a trigger on table B modifies table A that has its own write guard.
- **Owner bypasses DB write-guard triggers — all mutating Server Actions must enforce status checks at the app layer too.** `guard_item_pesanan_write` blocks writes on selesai/dibatalkan pesanan for helpers, but owners bypass it entirely. Without an explicit `status === 'diproses'` check in the action, an owner can mutate items on a closed pesanan. Apply this check in every action that writes `item_pesanan`, including the checklist toggles and the per-item price update.
- **Helpers may edit and delete items on ANY active pesanan, not just ones they created — this is intentional.** The per-creator ownership gate was removed from `guard_item_pesanan_write`; the shop's helpers work each other's orders, so the write guard only enforces "pesanan is still `diproses`" (plus the `pesanan_locked` setting), not authorship. `guard_pesanan_write` still restricts non-owner edits of the *pesanan* row itself to its creator. Don't "fix" the item guard back to a creator check without confirming the workflow change is wanted.
- **Client-supplied foreign-key IDs in Server Actions are untrusted for authorization.** When an action is keyed by an item ID but needs the parent `pesanan_id` (e.g. for revalidatePath or a status check), look up the real `pesanan_id` from the DB using the item ID — don't trust the `pesananId` the client passes alongside. A malicious or stale client value could bypass the status check or leak a path it shouldn't know about. **Delete the parameter from the signature rather than leaving it unused** — a still-accepted `pesananId` invites the next edit to reach for it again. Note that `@typescript-eslint/no-unused-vars` defaults to `args: 'after-used'`, so an unused middle parameter is *not* reported (only a trailing one is); lint being clean is not evidence that no vestigial ID remains. Item-keyed actions (`toggleItemDiambil`, `updateItemDetails`, `deleteItemFromPesanan`, `updateItemHarga`, …) take `itemId` and nothing else; only genuinely parent-keyed actions (`addItemToPesanan`, `resetChecklist`, `deletePesanan`) take a `pesananId`.
- **`?.` on a guard lookup is a fail-open. Destructure `error` and check it.** A guard that asks "is the target an owner?" via `const { data } = await ...; if (data?.role === 'owner') return { error }` treats a failed read as `null`, which is not `'owner'`, which proceeds. `deleteHelper` had exactly this shape in front of a `createAdminClient()` deletion that bypasses RLS — a transient lookup failure turned "refuse to delete an owner" into "delete the owner". The rule: when a lookup's *purpose* is to deny, an unreadable result must deny too. Same bug class as the settings gates below, and it does not show up in tests that only exercise the happy path — assert that the privileged call was **not** made.
- **A fail-closed action gate needs a fail-closed UI gate to match.** `requireUnlocked` correctly blocked helper mutations when `pesanan_locked` could not be read, but `getPesananLocked` returned `false` on the same failure, so the page rendered the unlocked affordances anyway — buttons whose only possible outcome was an error toast. When the enforcement layer fails closed, the layer that decides what to *show* must agree.
- **Fail-closed pattern for settings-based gates**: when a Server Action reads a `settings` row to decide whether to allow an operation (e.g. `pesanan_locked`), treat any DB error or missing row as a blocking condition — return an error rather than silently proceeding. A missing row means the table wasn't seeded correctly, which is an infrastructure problem that should surface, not be swallowed as "not locked."
- **`pesanan_locked` scope — helpers only, not owners.** The setting locks all helper mutations (add/edit/delete items, toggle checklists, reset checklist). Owners are only locked by `statusLocked` (order status). In `[id]/page.tsx` keep `statusLocked` and `isLocked` as separate variables; use `statusLocked` for owner-only UI like the per-item price editor and the owner Reset button, and `isLocked` (status OR settings-lock) for helper-facing UI. The `checkHelperLock()` helper in `actions.ts` centralizes the server-side check.
- **Local state mirroring a server value must be dropped when that server value changes — including state seeded once at mount.** `ItemChecklistCheckbox` and `HelperItemChecklist` do this with a render-phase `prev`-snapshot compare, and `ItemsSection`'s price editor now does too. It previously seeded `prices` for every item in a `useState` initialiser, so `rawPrice`'s `prices[id] ?? server` never fell through and the editor was pinned to its mount-time values permanently. Since `[id]/page.tsx` mounts `RealtimeRefresh` on the pesanan row, a price saved from another device pushed a new `items` prop the field ignored: it showed the stale number, the order total was derived from it, and blurring wrote that stale number back over the other device's save. Drop only the ids whose server value actually moved, so an edit in progress on another row survives. A `useState` initialiser runs once — it is not a sync mechanism. `CollyEditor`, `PengirimanEditor` and `TanggalPengirimanEditor` had the same bug (blur comparing a stale displayed value against a fresh `initialValue` prop, silently overwriting another device's save) and now carry the single-value form of the same fix: a `prevInitialValue` state compared during render.
- **Validate every row against its DB constraints *before* the parent insert.** `createPesanan` draws a kode, inserts the `pesanan` row, then inserts `item_pesanan`. `item_pesanan` carries `check (qty > 0)`, so a single qty-0 line committed the parent, burned a kode, failed the child insert and surfaced a raw Postgres constraint message — leaving an orphaned order with no items behind on every retry. The action now rejects blank `nama_barang` and non-integer/`< 1` qty up front, and `OrderForm`'s submit button applies the same rule (a newly added line starts at qty 0, so the obvious path hit this). `createPesanan` is now a single `create_pesanan_atomic` RPC (`20260805081656`), so the kode draw, the parent row and the lines share one transaction and a mid-sequence failure rolls all three back — verified live: a cast failure during the item insert left the kode counter and the row count unchanged. Keep the app-layer validation anyway: it answers in one round-trip and carries the Indonesian messages. Never reintroduce a direct `pesanan`/`item_pesanan` insert in this action.
- **`type="number"` inputs must store raw strings in state, not numbers.** `Number("") === 0` causes the input to re-render as `"0"`; on mobile the next keystroke appends instead of replaces, producing `"015"`. Pattern: `onChange={(e) => setState(e.target.value)}`, parse with `parseInt`/`parseFloat` only at save/calculation time, and initialise with `''` (not `0` or `1`) so the field starts empty. See `ItemsSection.tsx`.
- **`src/lib/database.types.ts` is generated from the live schema — regenerate it after every applied migration.** All three clients are `createClient<Database>()`, so a stale snapshot does not break the build; it makes the build pass while checking every query against a schema that no longer exists. Regenerate with the Supabase MCP `generate_typescript_types` tool for ref `pjkddahrjjqblexxhaef` and commit the result. `npm run types:check` (and CI) fails on any drift, comparing against the same Management API endpoint that MCP tool calls, so the bytes come from identical code — going via the `supabase gen types` CLI instead would add a version-skew failure indistinguishable from real drift. One known limitation: Postgres function parameters carry no nullability information, so RPC `Args` come out non-nullable even when the function accepts NULL — `createPesanan` widens them at the call site rather than editing the generated file.
- **Helper-facing selects cannot request a priced column: it is a compile error.** `itemsEmbed(false, columns)` constrains `columns` to `HelperSafeColumns<S>`, which tokenises the column list at the type level and collapses to `never` if it names `harga_satuan`, `subtotal` or `jumlah`. Tokenising is the point — a substring check would wrongly reject `jumlah_diambil`, which helpers do need. A widened `string` is refused too since it cannot be verified, so pass literals: `[id]/page.tsx` used to precompute one `itemsSelect` for both branches, and on the helper branch its type still included the owner's priced columns. Row types split the same way — `ItemPesananHelper` has no priced fields at all, `ItemPesananOwner` extends it with them, payments are `PembayaranOwner` only. `src/lib/pesanan-select.types.test.ts` pins both directions with `@ts-expect-error`, so weakening the constraint fails the build.
- **Price/payment columns are masked at the DB, not just in app code — all three phases are LIVE (applied 2026-08-01).** Postgres RLS restricts rows, not columns, and every signed-in user shares the one `authenticated` role, so RLS alone could never hide prices from a helper. Two layers now do:
  1. **App layer** — helper-facing selects ask for no priced column at all; an unfetched field can't reach the RSC payload. Encoded and tested in `src/lib/pesanan-select.ts`, not restated in call sites.
  2. **DB layer** — `20260801111127_price_column_masking_phase3_revoke.sql` revoked column `SELECT` on `harga_satuan`/`subtotal`/`jumlah` from `authenticated`. A helper hitting REST directly now gets `42501 permission denied`. Because owners are *also* just `authenticated`, owner reads go through `SECURITY DEFINER` views (`item_pesanan_owner`, `pembayaran_owner`, and `pesanan_unpaid_owner` — the dashboard's unpaid-orders list, added `20260802045800`, which aggregates the same masked columns) that re-check `current_user_role() = 'owner'` themselves, since they bypass RLS. Reading a priced column off the base table fails for everyone — that's intended, not a bug to route around. Any new view built the same way (SECURITY DEFINER + re-checks owner because it touches a masked column) must be added to `security_posture()`'s `owner_views` list (`20260805163157`, widened `20260820210400`) — a view left out is never asserted by `test:db`, which is exactly the gap `pesanan_unpaid_owner` sat in for two weeks.

  The rationale, threat model and post-apply verification live in `supabase/prepared/20260731_price_column_masking_APPLIED.sql`, which is a historical record with nothing left to apply.

  `anon` was closed off too in `20260805083315_price_column_masking_anon_revoke.sql`, which it had been left out of. `anon` and `authenticated` now hold identical `SELECT` column sets on both tables, so neither can read a price. Verified with the public anon key: `/rest/v1/item_pesanan?select=harga_satuan` returns `42501`, while `?select=nama_barang` returns `[]` — RLS blocking rows rather than a blanket table lockout.

  **The invariant is enforced by `npm run test:db`** (`scripts/db-security.test.ts`), which asserts against the live project that neither `anon` nor `authenticated` holds a column *or* table-level `SELECT` on the priced columns, that all three owner views (`item_pesanan_owner`, `pembayaran_owner`, `pesanan_unpaid_owner`) still re-check `current_user_role() = 'owner'` and are not `security_invoker`, and that the realtime publication is exactly `pesanan`/`pelanggan`/`users`. It reads the catalog through `public.security_posture()` (service-role only) and also probes REST with the public anon key. It never skips: placeholder credentials fail the suite, because a security check that passes when it cannot run is what created the four-day gap in the first place. Deliberately outside `npm run test:run`, which stays hermetic.

  Two things to know before touching these grants. `anon` and `authenticated` hold **table-level** SELECT by default in Supabase, and a column-level `REVOKE` does not remove a table-level grant — you have to revoke the table grant and re-grant the columns that stay readable (check `pg_class.relacl` for an `r`). And the `security_definer_view` ERROR advisories on `item_pesanan_owner`/`pembayaran_owner`/`pesanan_unpaid_owner` are intentional: the views must run as their owner or the revoke would apply to them too and defeat the whole design.
- **Row-level destructive actions (delete one pelanggan/pesanan/helper/payment) use `ConfirmDeleteButton` (`src/components/ConfirmDeleteButton.tsx`), not a hand-rolled confirmation.** Before this existed, the four delete buttons had four different confirmation UIs: native `window.confirm()` (`DeleteHelperButton`), an inline `confirming`-state toggle rendering separate confirm/cancel icon buttons in place (`DeletePelangganButton`/`DeletePesananButton`), and — worst — `DeletePaymentButton` had no confirmation at all, deleting immediately on click. `ConfirmDeleteButton` wraps the same `AlertDialog` primitives `ClearAllButton` already used, but as a single step (not `ClearAllButton`'s two-step "type to confirm"-style flow) — that extra friction is deliberately reserved for bulk "delete everything" actions, a different risk tier than deleting one row. Pass `renderTrigger` (the exact styled `Button`/`<button>` element, so each call site keeps its own visual style — icon-only ghost button vs. text link) and `triggerLabel` (its visible content) separately, since Base UI's `render` prop needs the real element, not a description of it.
- **Toggle buttons must show the action, not the current state.** A button labelled with what IS (e.g. "Terkunci") confuses users — they can't tell if clicking will change or confirm that state. Label with what WILL HAPPEN: "Kunci" when currently unlocked, "Buka Kunci" when currently locked. This is a recurring mistake; apply it to any toggle-style button in this codebase.
- **Multiple URL-param inputs must not each call `router.push` on `onChange`.** Each push triggers a navigation; the next push reads `useSearchParams()` before the previous navigation commits, so the second field's push overwrites the first field's value with the stale empty string. Pattern: hold both values in local `useState`, update on `onChange`, and push to the router on `onBlur`. See `DashboardDateFilter.tsx`.
- **Fixed/floating elements (FAB) need matching bottom padding on the scroll container.** The "Pesanan Baru" FAB is `fixed bottom-6 right-6` and covers page content on mobile. The `<main>` in `AppShell.tsx` uses `pb-24 sm:pb-6` to create clearance. Add the same offset whenever a new fixed element is introduced.
- **`sisaTagihan === 0` does not mean "Lunas" when `totalPesanan` is also 0.** An order whose items have no price yet has `sisaTagihan = 0 - 0 = 0`, which would show "✓ Lunas" — a false signal. Always gate the "Lunas" display on `totalPesanan > 0 || pembayaranList.length > 0`; otherwise show "Belum ada harga". See the Pembayaran section in `[id]/page.tsx`.
- **`beforeunload` only covers browser-level navigation (tab close, refresh, typed URL) — it never fires for `router.push`/`router.back()` or a `<Link>` click, since those are client-side transitions, not a real unload.** `OrderForm`'s unsaved-changes guard (an `isDirty` check gating a `beforeunload` listener) therefore needed a second, separate guard for its own in-app "Batal" button: `handleBatal` checks `isDirty` itself and shows an `AlertDialog` confirmation before calling `router.back()`, rather than relying on `beforeunload` to catch that path too. This app's Next version has no App Router API to intercept arbitrary in-app navigations (e.g. a Sidebar link click away from an unsaved form) — only the explicit in-component action can be guarded this way.
- **Client-component pages cannot export `metadata`.** `'use client'` files silently ignore `export const metadata`. Wrap the page in a server-component `layout.tsx` for the route group (e.g. `src/app/(auth)/layout.tsx`) and export `metadata` there instead.
- **`@react-pdf/renderer` images in browser context require base64 data URIs, not relative paths.** `pdf()` runs in its own non-DOM reconciler and cannot reliably resolve `/public/image.jpg` paths. Fetch images before calling `pdf()` and convert them: use `canvas.toDataURL('image/png')` for images that need cropping/transformation, or `FileReader.readAsDataURL(blob)` for images served as-is. A4 page dimensions for absolute positioning: 595.28 × 841.89 PDF points; use `position: 'absolute'` + `opacity` on an `<Image>` for watermarks.
- **`autoFocus` pattern for dynamically added list items.** To focus the first input of a newly added item (e.g. "Tambah Barang" adding a row), track the last-added item's id: `const [lastAddedId, setLastAddedId] = useState<string | null>(null)`, set it when creating the item, then pass `autoFocus={item.id === lastAddedId}` to the input. Since `autoFocus` fires only on initial mount, it focuses exactly the new item without disturbing others.
- **Deduplicate repeated auth/role DB queries with React `cache()`.** The `(app)` layout and every page both need the current user's role. Without caching, each Server Component fires its own round-trip. Wrap the fetch in `cache()` from `'react'` (`src/lib/supabase/request-cache.ts` exports `getCurrentUser`, `getAuthUser`, `getPesananLocked`); React deduplicates calls with the same arguments within one render tree, so only one DB query fires per request regardless of how many Server Components call them. **Do not call these from Server Actions** — Actions run outside the render tree and don't share the cache scope.
- **Parallelize independent Supabase queries in Server Components with `Promise.all()`.** Any two queries whose results don't depend on each other should run concurrently. Pattern: `const [{ data: a }, { data: b }] = await Promise.all([supabase.from('a').select(...), supabase.from('b').select(...)])`. Common cases: fetching a pesanan + the lock setting in `[id]/page.tsx`; fetching the user list + lock setting in `pengaturan/page.tsx`; the two pesanan queries (all-time vs period) in `dashboard/page.tsx`.
- **Replace two-query item→pesanan lookups with a single join.** `getItemPesananStatus` previously did two sequential queries (fetch item to get `pesanan_id`, then fetch pesanan to get `status`). Use a nested select instead: `supabase.from('item_pesanan').select('pesanan_id, pesanan:pesanan(status)').eq('id', itemId)` — one round-trip, same data. Apply this pattern whenever you need parent-table data keyed by a child-table row.
- **`error.tsx` / `global-error.tsx` take `unstable_retry`, not `reset` (Next 16.2+).** Both props are passed, so declaring only `reset` type-checks and builds clean — but `reset` is just `setState({ error: null })`, which re-renders the *same already-failed RSC payload*. `unstable_retry` is `startTransition(() => { router.refresh(); reset() })`, i.e. it actually refetches. Every boundary in this app recovers from a failed Supabase query in a Server Component, so `reset` alone makes "Coba Lagi" a no-op. Nothing catches this: Next's generated `.next/types/validator.ts` type-checks page/layout signatures only — never `error.tsx` — so `npm run build` is silent on it.
- **Helper-facing mutations use the combined gate from `pesanan-guards.ts`, not a hand-rolled sequence.** `requireHelperCanMutateItem(supabase, itemId)` / `requireHelperCanMutatePesanan(supabase, pesananId)` bundle the three checks every such action needs — authenticated → `pesanan_locked` (helpers only) → parent pesanan still `diproses` — and run the role and row lookups concurrently. Hand-rolling them is how the call sites drifted before: some parallelized, some serialized four round-trips, and all of them validated the session twice (once directly, once inside the lock check). Owner-only actions still use `requireOwner` + `requireActivePesanan`, since owners skip the lock but not the status check. `requireUnlocked(supabase, role, message?)` is the standalone lock read for the one action (`createPesanan`) that has no row to check yet.
- **A Server Action whose callers read `result.error` *and* `result.pesananId` needs an explicit return type.** TypeScript only synthesises the implicit `error?: undefined` / `pesananId?: undefined` members of an inferred return union when *every* return is a fresh object literal. The moment one branch returns a guard's result variable, the union narrows and every `result.error` at the call site becomes a compile error in an apparently unrelated file. Declare `Promise<{ error?: string; pesananId?: string }>` rather than relying on inference. Note `npm run build` surfaces this but `npm run test:run` and `npm run lint` do not.
- **A list component that owns per-row input state must memoise its per-row children.** `ItemsSection` holds the price-input state for every row and renders the list twice (a `sm:hidden` card list plus a `hidden sm:block` table, both always mounted), so one keystroke re-rendered every checklist control on the order — 4 renders per item per keystroke, 800 wasted renders on a 40-item order. `ItemChecklistCheckbox` and `HelperItemChecklist` are `memo()`-wrapped; their props are all primitives, so the default shallow compare is correct and no `useCallback` is needed at the call sites. Measure this by counting renders of something *inside* the memo boundary (the tests count `Checkbox` renders) — wrapping the child in a counting component puts the counter outside the boundary and always reports zero benefit. `OrderForm` had the same shape: its desktop table already routed through the memoised `OrderLineItem`, but its `sm:hidden` mobile card list inlined the row markup directly in `.map()` instead of a component, so it had no memo boundary to skip on unrelated keystrokes. Fixed by extracting `OrderLineItemCard` (same `memo()`-wrapped pattern, in `OrderLineItem.tsx`) — when adding a second (e.g. mobile-card) rendering of an existing memoised list, always give the new layout its own memoised child component rather than inlining.
- **Hoist filter-invariant work out of the row predicate, and precompute search text.** `OrderList` re-parsed both date bounds inside its `.filter()` callback, so a keystroke with a date range active cost ~1000 extra `parseISO`/`startOfDay` calls over a 500-order list — 1.86ms per keystroke, versus 0.011ms once hoisted. Lowercased search text is likewise built once per list in a `useMemo` keyed on the rows alone, not once per field per keystroke. When concatenating fields into one haystack, join with an escaped NUL (`\u0000`): a plain space lets a query match across the field boundary and silently widens what search does.
- **Reduce embedded rows to their aggregates on the server before handing them to a Client Component.** `OrderList` only ever collapsed each order's `items`/`pembayaran` into four numbers, yet the page serialised every embedded row into the RSC payload — ~47% of it at six items/order. `toOrderRows()` does that projection in the Server Component and passes `{ p, view }`, where `p` carries only the fields the markup renders. When a client component's prop is an array it just reduces or counts, project it server-side. Rebuilding the object field-by-field (rather than spreading) also keeps unrequested columns out of the payload, the same rule the per-role selects follow.
- **Replace sequential N+1 loops with `Promise.all()` in Server Actions.** Loops like `for (const item of items) { await supabase.update(...) }` do N sequential round-trips. Replace with `await Promise.all(items.map(item => supabase.update(...)))` to run all updates concurrently. Used in `clearAllPelanggan`. If any single update failing should abort the whole operation, check `results.find(r => r.error)` after the `Promise.all`.
